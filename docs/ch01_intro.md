# 1. 게임 서버 프로그래밍

## 1.1 교재의 목적과 학습 범위

본 교재는 게임 엔진이 제공하는 네트워크 기능을 활용하는 단계에서 시작하여, C++ 기반 통신 모듈을 응용한 방(Room) 중심 분산 게임 서버를 설계·구현하는 데 목적이 있다. 네트워크 게임의 구현 방법과 서버 아키텍처를 연결해 이해하는 실습 중심 교재이다.

대상 독자는 C++ 객체지향 프로그래밍, TCP/IP, 소켓, 스레드 및 데이터베이스 기초를 이수한 학습자이다. 이미 학습한 Windows 네트워크 프로그래밍이나 데이터베이스 개론을 처음부터 반복하지 않고, 게임 서버에 적용하는 방법에 집중한다.

교재의 최종 완성 목표는 Distributed MO Game Server(방 기반 분산형 게임 서버)이다. Seamless World 및 대규모 MMORPG 월드 분산은 후속 심화 주제로 남긴다. 교재 전체를 한 학기에 모두 구현하는 것을 전제로 하지 않으며, 강의에서는 학습 수준에 맞는 장과 프로젝트를 선택한다.

### 1.1.1 이 교재를 마치면 할 수 있는 것

이 교재는 다음 네 가지 능력을 목표로 한다.

- 서버가 하는 일(접속자 관리와 메시지 중계)을 설명하고, 접속·종료·재접속 흐름을 구현한다.
- Unity Netcode for GameObjects, Unreal Dedicated Server, Steam Listen Server라는 세 가지 구현 경로의 구조와 한계를 비교한다.
- 게임 데이터의 성격에 따라 RDBMS, NoSQL, 분산 SQL 중 저장소를 선택하고 그 근거를 설명한다.
- Asio 기반 C++ 네트워크 모듈로 Gateway, Lobby/Room Manager, 복수의 Game Server를 구성하여 방 기반 분산 게임 서버를 구현하고 부하를 측정한다.

### 1.1.2 서버의 역할과 이 교재의 범위

상용 게임 서버는 게임 규칙의 판정까지 서버에서 처리한다. 그러나 이 교재의 엔진 파트(2~4장)는 각 게임 엔진에서 서버를 어떻게 구성하는가를 배우는 것이 목표이므로, 게임 규칙은 클라이언트(소유한 플레이어 또는 호스트)에서 처리하고 서버는 메시지 중계와 접속자 관리를 담당한다.

접속자 관리는 접속 승인과 정원 제한, 접속자 ID와 플레이어 오브젝트의 부여, 접속자 목록의 유지, 입장·퇴장 통지, 연결 종료의 감지와 재접속을 뜻한다.

서버가 게임 규칙을 판정하고 클라이언트 요청을 검증하는 방식은 상용 서비스의 핵심이지만 학습 범위를 크게 넓히므로, 엔진 파트에서는 개념으로 소개하고 방 기반 서버를 직접 구현하는 6장에서 다룬다.

### 1.1.3 교재 사용 방법

각 장은 학습 목표, 핵심 개념, 단계별 실습, 점검 항목의 순서로 구성한다. 실습 항목에는 [구현 순서], [확인할 것], [흔한 오류]를 붙여 학습자가 스스로 결과를 점검할 수 있게 한다. 코드는 고정폭 글꼴로 표기하고 핵심 동작을 보이는 최소 분량만 싣는다. 예제 코드는 장별로 시작 코드와 완성 코드를 구분하여 제공한다. [저장소 주소는 집필 시 기재]

게임 엔진과 라이브러리는 버전에 따라 API와 설정 방식이 달라지므로, 본문의 설명은 개념을 중심으로 하고 코드는 아래 환경에서 검증한 버전을 기준으로 한다. 각 장 서두에 실제 검증한 버전을 다시 기재한다.

- 운영체제와 도구: Windows, Visual Studio [버전 기재]
- Unity: Unity Editor [버전], Netcode for GameObjects [버전], Unity Transport [버전], Multiplayer Tools [버전]
- Unreal: Unreal Engine [버전], C++ 빌드 환경(Visual Studio)
- Steam: Steamworks SDK [버전], 개발용 App ID [확인 후 기재]
- 서버: C++20, Asio(standalone) [버전], MySQL 또는 MariaDB, Redis, MongoDB [버전]

### 1.1.4 다루지 않는 범위

이 교재는 Windows 네트워크 프로그래밍과 데이터베이스 개론의 기초를 다시 설명하지 않는다. Seamless World, Zone 간 객체 이전, 고급 장애 복구는 6.9절의 제외 범위에 따라 후속 주제로 남긴다. 또한 Steam 스토어 등록과 심사, 상용 서비스 운영(Linux 서버 운영, 컨테이너 배포, CI/CD)은 본문의 범위에 넣지 않는다.

[NCS 검토에서 추가한 점] 위 범위 가운데 서버를 만든 뒤 실행하고 배포하는 최소한의 절차는 6장에서 한 번씩 다룬다. systemd로 서버를 서비스로 등록하는 예(6.14.5절), 서버를 하나씩 교체하고 되돌리는 절차(6.14.6절), CI가 실행할 명령(6.14.7절)이다. 컨테이너 배포, CI 서비스의 설정, 상용 서비스 운영 도구는 범위 밖으로 남긴다.

## 1.2 게임 서버의 분류

호스팅 방식: Listen Server는 게임에 참여하는 플레이어가 서버 역할을 겸하며, Dedicated Server는 게임 플레이 클라이언트와 분리된 서버 프로세스로 운영된다. P2P는 통신 토폴로지, Relay는 통신 중계 방식이므로 Listen/Dedicated와 같은 단일 분류 축으로 취급하지 않는다.

게임 공간 구조: Room-Based는 독립적인 게임 방, Instance-Based는 던전이나 필드의 개별 인스턴스, Zone-Based는 월드의 지역 분할, Seamless World는 지역 이동을 연속적으로 경험하도록 구성하는 방식이다. 실제 게임은 여러 구조를 혼합할 수 있다.

시스템 아키텍처: 단일 프로세스 서버, 다중 게임 인스턴스 서버, 기능별 다중 프로세스 서버, 방 기반 분산 서버, Zone 기반 분산 월드 서버 등으로 구분할 수 있다. 서버 프로세스가 여러 개라는 사실만으로 곧바로 심리스 월드가 되는 것은 아니다.

MO와 MMO는 게임 서비스 규모 및 플레이 형태를 나타내는 관용적인 용어로, 고정된 서버 구현 모델이 아니다. 이 교재에서는 기술 범위를 명확히 하기 위해 '방 기반 분산형 게임 서버(Room-Based Distributed Game Server)'를 최종 프로젝트 명칭으로 사용한다.

### 1.2.1 서버가 하는 일: 중계와 접속자 관리

멀티플레이 게임에서 서버의 본질은 프로세스가 어디에서 실행되는가가 아니라 어떤 일을 맡는가에 있다. 이 교재의 엔진 파트(2~4장)에서 서버는 다음 두 가지를 맡는다.

- 중계: 한 클라이언트가 보낸 상태와 이벤트를 다른 클라이언트에게 전달한다. 게임 규칙의 계산은 하지 않는다.
- 접속자 관리: 접속 승인과 정원 제한, 접속자 목록, 입장·퇴장 통지, 연결 종료의 감지와 재접속을 처리한다.

Listen Server에서는 한 플레이어의 클라이언트가 서버 역할을 겸하므로 이 일을 호스트가 맡는다. Dedicated Server는 이 일만 하는 별도 프로세스이다. 호스트가 종료되면 세션이 끝나는 점이 둘의 중요한 차이이다.

게임 규칙을 클라이언트에서 처리하면 구현이 단순한 대신 클라이언트의 조작에 취약하다. 상용 서비스는 서버가 규칙을 판정하는 방식을 사용하며, 이 한계를 알고 선택한다는 점만 짚고 넘어간다.

### 1.2.2 네트워크 게임을 설계하는 세 가지 질문

어떤 방식으로 구현하든 네트워크 게임의 설계는 다음 질문으로 정리할 수 있다.

- 누가 접속해 있는가(접속자 관리): 접속 승인, 정원, 접속자 목록, 종료와 재접속을 누가 처리하는가.
- 상태는 누가 갖고 누구에게 보내는가(소유와 동기화): 오브젝트의 원본 상태가 어디에 있고, 어떤 방식과 주기로 다른 참가자에게 전달하는가.
- 지연과 장애가 생기면 무엇이 보이는가(견고성): 지연, 패킷 손실, 접속 종료, 중도 참여, 재접속 상황에서 게임이 어떻게 동작하는가.

각 장은 이 세 질문에 서로 다른 수준으로 답한다.

- 2장 Unity: 엔진의 네트워크 객체 모델로 세 질문의 기본 형태를 경험한다.
- 3장 Unreal: 복제와 RPC가 엔진 구조에 더 엄격하게 반영된 방식을 경험한다.
- 4장 Steam: 별도 서버가 없을 때 호스트가 서버 역할을 하는 구조와, 연결 서비스와 게임 로직의 책임 분리를 다룬다.
- 5장 Game Database: 영속 데이터의 원본이 어디에 있고 일관성을 어떻게 지키는가를 다룬다.
- 6장 Distributed MO Game Server: 상태의 소유자를 여러 서버 프로세스에 나누고, 엔진이 해 주던 일을 C++로 직접 구현한다.

### 1.2.3 이 교재의 분류상 위치

앞의 분류 기준으로 이 교재의 실습을 정리하면 다음과 같다.

- 호스팅 방식: 2장은 Host와 Dedicated(Server) 모두 구동하고, 3장은 Dedicated Server, 4장은 Listen Server, 6장은 자체 Dedicated 서버 프로세스를 사용한다.
- 게임 공간 구조: 2~4장은 단일 방(Room) 규모이며, 6장에서 여러 Room을 여러 Game Server에 배치한다.
- 시스템 아키텍처: 2~4장은 단일 프로세스 서버이고, 6장에서 기능별 다중 프로세스와 방 기반 분산 구조를 구현한다.

## 1.3 교재의 구성

Part 1 — Unity Game Server: Unity Netcode를 활용하여 호스트/클라이언트와 게임 상태 동기화를 학습한다.

Part 2 — Unreal Game Server: Unreal Dedicated Server와 서버 권한·복제·RPC 구조를 학습한다.

Part 3 — Steam Listen Server: C++ 소켓 기반 호스트 서버 실습에서 시작하여 Steam Networking Sockets, Unity Netcode 및 Unreal Listen Server와 Steamworks를 연동한 온라인 게임을 구현한다.

Part 4 — Game Database: 게임 데이터에 필요한 RDBMS, NoSQL, NewSQL/Distributed SQL의 특징과 적용 기준을 학습한다.

Part 5 — Distributed MO Game Server: Asio 기반 네트워크 모듈을 사용하고 Gateway·Lobby·Room·Game Server를 분리하여 방 기반 분산 서버를 구축한다.

### 1.3.1 Part 사이의 연결

이 교재에서 Part 1~5는 각각 2~6장에 해당한다. 앞 장은 뒤 장의 전제가 되며, 엔진이 대신 처리해 주던 일을 단계적으로 학습자에게 드러내는 순서로 구성한다.

- 2~3장: 엔진이 연결 관리, 객체 식별, 상태 복제, RPC를 대신 처리한다. 학습자는 이 기능으로 서버를 구성하고 접속자를 관리하는 방법에 집중한다.
- 4장: 연결 계층을 Steam으로 교체하고, 일반 소켓 코드를 직접 작성하여 연결과 게임 로직의 경계를 확인한다.
- 5장: 게임 서버가 다루는 영속 데이터의 저장소 선택과 일관성 문제를 다룬다.
- 6장: 연결, 세션, 패킷, 실행 모델을 C++ 모듈로 직접 구현하고 여러 프로세스로 확장한다.

### 1.3.2 장별 최종 산출물

- 2장: 2~4인 규모의 협동 또는 대전 게임(Unity)
- 3장: 4~8인 규모의 멀티플레이 액션 게임(Unreal Dedicated Server)
- 4장: Steam 로비와 친구 초대로 접속하는 Listen Server 게임(C++, Unity, Unreal 각 1종)
- 5장: 계정과 게임 결과의 저장 구조와 Redis 적용 예
- 6장: 방 기반 분산 게임 서버 일체와 테스트용 클라이언트, 프로토콜 정의, 서버 구성도, 스키마, README

## 1.4 게임 서버 아키텍처의 기본

이 절은 이후 모든 장의 바탕이 되는 개념을 정리한다. 엔진이 대신 처리해 주는 부분도 결국 아래의 원리를 구현한 것이므로, 엔진 기능을 쓰기 전에 원리를 알아 두면 문제가 생겼을 때 원인을 찾을 수 있다.

### 1.4.1 클라이언트-서버, P2P, 릴레이

클라이언트-서버: 모든 클라이언트가 한 서버에 연결하고 서버를 거쳐 서로 통신한다. 연결 수가 N이면 서버가 유지할 연결도 N개이다. 상태의 기준(원본)을 한곳에 둘 수 있어서 일관성과 보안에 유리하고, 상용 온라인 게임의 대부분이 이 구조이다. 단점은 서버 운영 비용과 서버가 단일 장애 지점이 된다는 점이다.

P2P(Peer-to-Peer): 참가자끼리 직접 연결한다. N명이 전부 서로 연결하면 연결은 N(N-1)/2개로 늘어나므로 소규모 게임에 적합하다. 서버 비용이 없지만 상태의 기준이 없어 참가자마다 상태가 어긋날 수 있고, 각 참가자의 IP가 서로 노출되며, 방화벽과 NAT 때문에 직접 연결이 안 되는 경우를 따로 처리해야 한다. 격투 게임의 롤백 넷코드처럼 모든 참가자가 같은 입력으로 같은 결과를 계산하는 결정론적(lockstep) 방식에서 주로 쓴다.

릴레이: 직접 연결이 어려운 참가자들을 중간 서버가 패킷만 전달해 연결한다. 게임 규칙을 계산하지 않고 전달만 하는 점에서 이 교재의 '중계'와 같은 개념이다. Steam의 Datagram Relay(SDR)가 대표적이다.

```text
 [Client-Server]          [P2P (N=4)]            [Relay]
   C1   C2                 P1 --- P2               P1     P2
     \ /                    | \ / |                  \   /
      S                     | / \ |                   Relay
     / \                   P3 --- P4                  /   \
   C3   C4             연결 6개                     P3     P4
```

권한(Authority): 어떤 값의 원본을 가진 쪽이 그 값을 바꿀 권리를 갖는다. 서버가 원본을 가지면 서버 권한(server authoritative), 소유한 클라이언트가 원본을 가지면 클라이언트 권한(owner authoritative)이라 한다. 2장의 NetworkTransform을 Owner 권한으로 두는 것은 후자이다. 서버 권한은 조작 방지에 강하지만 입력이 서버를 왕복하는 만큼 반응이 늦어 보이므로 2.16.7절의 클라이언트 예측이 필요해진다.

### 1.4.2 서버가 하는 일의 단계

게임 서버가 맡는 일은 단계로 나누면 이해하기 쉽다. 이 교재는 아래 단계를 순서대로 올라간다.

1단계, 연결 관리: 접속을 받고, 끊김을 감지하고, 접속자 목록을 유지한다. 2~4장의 서버가 하는 일이다.

2단계, 중계: 받은 메시지를 필요한 대상에게 전달한다. 전체 전송(broadcast), 특정 방 전송, 일대일 전송을 구분한다.

3단계, 상태 관리: 게임 오브젝트의 위치와 체력 같은 상태를 서버가 갖고 갱신한다.

4단계, 규칙 판정: 클라이언트가 보낸 요청이 규칙에 맞는지 서버가 검증하고 결과를 결정한다. 6장에서 일부 구현하고, 상용 서비스는 이 단계가 핵심이다.

5단계, 영속화와 운영: 결과를 데이터베이스에 저장하고, 서버 여러 대를 관리하고, 장애에 대응한다. 5~6장의 내용이다.

### 1.4.3 틱(Tick)과 상태 전송

서버는 연속적으로 상태를 보내는 것이 아니라 일정한 간격으로 갱신하고 전송한다. 이 간격이 틱이다. 틱 비율은 게임마다 다르며, 초당 20~60회가 흔하다. 틱을 높이면 반응은 좋아지지만 CPU와 대역폭이 그만큼 늘어난다.

예를 들어 서버 틱이 30Hz이면 한 틱은 약 33ms이다. 한 틱 안에 입력 처리, 시뮬레이션, 전송 준비가 모두 끝나야 하며, 끝나지 않으면 틱이 밀려 모든 플레이어의 지연이 커진다. 따라서 서버 개발에서는 한 틱의 처리 시간 예산을 정하고 측정하는 습관이 필요하다.

상태 전송 방식은 크게 두 가지이다.

- 상태 동기화(state synchronization): 오브젝트의 현재 상태(위치, 회전, 체력)를 주기적으로 보낸다. 패킷이 몇 개 사라져도 다음 패킷이 현재 상태를 덮어쓰므로 견고하다. NGO의 NetworkVariable, Unreal의 변수 복제가 이 방식이다.
- 이벤트 전송(event/RPC): 발사, 피격, 채팅처럼 한 번 일어난 일을 보낸다. 사라지면 안 되므로 신뢰성 있는 전송이 필요하다.

자주 바뀌는 값은 상태로, 한 번만 일어나는 일은 이벤트로 보내는 것이 기본 원칙이다. 반대로 하면(예: 위치를 이벤트로 매번 보내거나 발사를 상태로 보내면) 대역폭이 낭비되거나 일부 클라이언트가 일을 놓친다.

## 1.5 네트워크 특성과 전송 프로토콜의 선택

### 1.5.1 지연, 지터, 손실, 대역폭

게임 네트워크의 품질은 네 가지 값으로 나타낸다.

- 지연(latency): 패킷이 한 방향으로 가는 데 걸리는 시간. 보통 왕복 시간(RTT, Round Trip Time)으로 측정한다. 같은 지역의 서버는 수십 ms, 대륙 간은 100ms를 넘기도 한다. 광속의 한계 때문에 거리가 멀면 줄일 수 없다.
- 지터(jitter): 지연의 흔들림. 평균 지연이 같아도 지터가 크면 움직임이 끊겨 보인다. 보간 버퍼(2.16.5절)가 지터를 흡수하는 데 쓰인다.
- 패킷 손실(packet loss): 도중에 사라지는 패킷의 비율. 무선 환경에서 흔하다. 1~2%만 되어도 TCP 기반 통신은 재전송 때문에 눈에 띄게 느려질 수 있다.
- 대역폭(bandwidth): 단위 시간당 보낼 수 있는 데이터 양. 서버에서는 접속자 수에 비례해 늘어나므로 비용과 직결된다. 예를 들어 클라이언트 한 명에게 초당 30번, 한 번에 200바이트를 보내면 약 6KB/s이고, 1,000명이면 약 6MB/s(약 48Mbps)이다.

이 값들은 2.13절과 3.4절에서 지연 시뮬레이션 도구(Unity Network Simulator, Unreal Net PktLag 등)로 직접 만들어 보고 게임이 어떻게 변하는지 확인한다.

### 1.5.2 TCP와 UDP

TCP는 순서와 도착을 보장한다. 대신 패킷 하나가 사라지면 뒤따르는 데이터가 모두 기다린다(Head-of-Line Blocking). 위치 같은 실시간 상태에서는 이미 낡은 데이터를 기다리느라 최신 데이터가 늦게 도착하는 문제가 생긴다. 또 Nagle 알고리즘이 작은 패킷을 모아 보내므로 게임에서는 보통 TCP_NODELAY를 켠다.

UDP는 순서와 도착을 보장하지 않지만 지연이 일정하고 낡은 패킷을 무시할 수 있다. 대신 신뢰성이 필요한 부분은 응용 계층에서 직접 만든다. 대부분의 액션 게임이 UDP 기반 프로토콜을 쓰는 이유이다.

- 로그인, 상점, 거래, 채팅처럼 순서와 도착이 중요한 요청은 TCP(또는 신뢰성 있는 채널)가 적합하다.
- 위치, 회전, 입력처럼 자주 보내고 최신 값만 의미 있는 데이터는 UDP(비신뢰 채널)가 적합하다.

실제 게임은 두 가지를 섞는다. Unity Transport와 Unreal은 UDP 위에 신뢰 채널과 비신뢰 채널을 함께 제공하고, Steam Networking Sockets도 메시지마다 신뢰/비신뢰 플래그를 지정한다. 이 교재의 6장은 학습 목적으로 TCP 기반 서버를 구현하며, 이때 위치 전송처럼 빈번한 데이터에서 HOL Blocking이 생길 수 있다는 한계를 알고 쓴다.

QUIC은 UDP 위에 TLS와 다중 스트림을 얹은 프로토콜로, 스트림별로 HOL Blocking을 피한다. 게임 전용 라이브러리에는 ENet, KCP, RakNet 계열(신뢰성 있는 UDP)이 있다. 이 교재는 새 프로토콜을 만들지 않고 존재 여부와 용도만 소개한다.

## 1.6 패킷 설계와 직렬화

### 1.6.1 패킷 프레이밍

TCP는 바이트 스트림이므로 메시지의 경계가 없다. 한 번 send한 데이터가 한 번 recv로 오지 않고, 쪼개지거나 붙어서 도착한다. 그래서 모든 패킷에 길이를 담은 헤더를 붙이고, 수신 측은 (1) 헤더 크기만큼 모으고, (2) 헤더의 길이만큼 본문을 모은 뒤, (3) 한 패킷으로 처리하는 과정을 반복한다. 6장의 서버가 이 방식(길이 2바이트 + 종류 2바이트)을 쓴다.

```text
[size:2][type:2][body: size bytes]   [size:2][type:2][body ...]
|<-- header -->|                      다음 패킷
```

- 최대 길이를 정하고 넘으면 연결을 끊는다. 악의적으로 큰 길이를 보내 서버 메모리를 소모시키는 공격을 막기 위해서이다.
- 바이트 순서(endian)를 정한다. x86/x64는 리틀 엔디언이므로 보통 리틀 엔디언으로 통일하고, 다른 구조와 통신할 가능성이 있으면 네트워크 바이트 순서(빅 엔디언)로 변환한다.
- 구조체를 통째로 memcpy하지 않는다. 컴파일러마다 패딩이 다르고, 포인터나 가상 함수가 들어 있으면 의미가 없다. 필드를 하나씩 직렬화한다.

### 1.6.2 직렬화 방식의 선택

- 문자열(텍스트) 프로토콜: JSON처럼 사람이 읽을 수 있다. 디버깅이 쉽지만 크기가 크고 파싱이 느리다. 로그인이나 관리용 API에 적합하다. 이 교재의 6장은 학습 편의를 위해 본문을 단순한 문자열로 쓴다.
- 직접 만든 바이너리 프로토콜: 필드 순서와 크기를 정해 쓰고 읽는다. 가장 작고 빠르지만 버전 호환과 오류 방지를 직접 관리해야 한다. 실시간 상태 전송에 흔하다.
- Protocol Buffers, FlatBuffers 같은 스키마 기반 직렬화: 스키마 파일에서 코드를 생성한다. 필드를 추가해도 이전 버전과 호환되기 쉽고 여러 언어가 같은 정의를 쓸 수 있다. FlatBuffers는 역직렬화 없이 바로 읽는 방식이다.

대역폭을 줄이는 기법도 알아 둔다. 실수를 고정 소수점이나 16비트로 양자화(quantization)하고, 이전 상태와 달라진 필드만 보내고(델타 압축), 한 번에 여러 메시지를 묶어 헤더 오버헤드를 줄인다. 위치 하나를 float 3개(12바이트) 대신 범위가 정해진 16비트 정수 3개(6바이트)로 보내면 절반이 된다.

### 1.6.3 프로토콜 버전과 호환성

서버와 클라이언트는 따로 배포되므로 같은 시점에 같은 버전이 아닐 수 있다. 접속 시 첫 패킷에 프로토콜 버전을 넣어 서버가 맞지 않는 클라이언트를 정중하게 거부하고(업데이트 안내), 새 필드는 끝에 추가하고 기존 필드는 의미를 바꾸지 않는 규칙을 둔다. 알 수 없는 패킷 종류는 연결을 끊지 않고 무시하거나 기록한다.

## 1.7 서버의 실행 모델

### 1.7.1 게임 루프

서버는 고정된 간격으로 반복하는 루프를 가진다. 기본 구조는 다음과 같다.

```cpp
while (running)
{
    now = Clock();
    ProcessNetworkInput();        // 쌓인 패킷을 꺼내 처리
    while (accumulator >= dt)     // 고정 시간 간격으로 갱신
    {
        Update(dt);               // 게임 로직
        accumulator -= dt;
    }
    SendSnapshots();              // 필요한 클라이언트에 상태 전송
    SleepUntilNextTick();         // 남은 시간 대기
}
```

간격이 고정되어 있어야 시뮬레이션 결과가 장비 성능에 흔들리지 않고, 틱마다 처리 시간을 측정할 수 있다. 처리가 한 틱을 넘으면 로그를 남기고 원인을 찾아야 한다.

### 1.7.2 스레드 모델

- 단일 스레드: 모든 일을 한 스레드가 처리한다. 잠금이 필요 없고 디버깅이 쉽다. 방 하나가 수십 명 규모이면 충분한 경우가 많고, 여러 코어는 방(또는 프로세스)을 여러 개 띄워 활용한다.
- I/O 스레드와 로직 스레드 분리: 네트워크 입출력은 I/O 스레드가 맡고, 받은 패킷을 큐에 넣으면 로직 스레드가 꺼내 처리한다. 게임 데이터를 로직 스레드 하나만 건드리므로 잠금이 필요 없다. 6장의 구조이다.
- 스레드 풀과 공유 데이터: 여러 스레드가 같은 데이터를 만진다. 성능 여지가 있지만 교착 상태와 경쟁 조건 위험이 크다. 꼭 필요한 부분에만 쓰고, 잠금 범위를 짧게 유지한다.

핵심 원칙은 한 데이터를 한 스레드가 소유하게 하는 것이다. 다른 스레드가 필요하면 직접 만지지 않고 메시지(작업)를 큐로 보낸다. 이렇게 하면 잠금 없이 안전하고, 이후 프로세스를 나눌 때도(6장) 같은 방식이 그대로 확장된다.

### 1.7.3 블로킹 작업의 분리

데이터베이스 질의, 파일 입출력, 외부 HTTP 호출은 수 ms에서 수백 ms가 걸릴 수 있다. 이런 작업을 게임 루프에서 직접 호출하면 그동안 모든 플레이어의 게임이 멈춘다. 별도 작업 스레드로 보내고 결과를 큐로 돌려받아야 한다. 5장의 DB Worker가 이 구조이다.

## 1.8 보안과 신뢰 경계

클라이언트는 신뢰하지 않는다는 원칙이 서버 보안의 출발점이다. 클라이언트 프로그램은 사용자의 컴퓨터에서 실행되므로 메모리 조작, 패킷 위조, 속도 조작 같은 부정 행위를 막을 수 없다고 가정한다.

- 입력 검증: 패킷의 길이, 종류, 값의 범위를 모두 서버가 확인한다. 잘못된 패킷은 무시하거나 연결을 끊는다. 서버가 죽는 입력(버퍼 오버런, 0으로 나눔, 무한 반복)이 없어야 한다.
- 규칙 판정: 이동 속도, 사거리, 쿨다운, 아이템 수량 같은 게임 규칙을 서버가 확인한다. 클라이언트가 "내 체력이 100이다"라고 보내는 것이 아니라 "공격했다"는 요청을 보내고 서버가 결과를 계산한다.
- 인증과 세션: 로그인 후 서버가 발급한 토큰으로 이후 요청을 식별한다. 비밀번호는 평문으로 저장하지 않고 솔트를 포함한 해시로 저장한다(5장). 로그인 같은 민감한 통신은 TLS로 보호한다.
- 속도 제한: 한 연결이 단위 시간에 보낼 수 있는 패킷 수와 크기를 제한하여 서비스 거부(DoS) 공격과 오작동 클라이언트로부터 서버를 보호한다.
- 노출 최소화: 보이지 않는 곳의 적 위치처럼 클라이언트가 알 필요 없는 정보는 보내지 않는다(월핵 방지).

2~4장의 채팅 프로그램에서 인증 코드와 이름 중복 검사를 하는 이유도 같은 원칙의 가장 작은 예이다.

## 1.9 운영과 측정

서버는 만들고 끝이 아니라 돌리면서 고친다. 게임 서버 프로그래머가 갖춰야 하는 운영 기본기를 정리한다.

- 로그: 접속, 종료, 오류, 느린 틱을 시간과 연결 ID와 함께 남긴다. 로그 레벨(정보, 경고, 오류)을 나누고, 디버그 로그는 운영 중에 끌 수 있게 한다. 개인정보와 비밀번호는 남기지 않는다.
- 지표(metrics): 동시 접속자 수, 틱 처리 시간, 초당 패킷 수, 대역폭, 메모리, 큐 길이를 주기적으로 기록한다. 문제를 추측하지 않고 숫자로 확인하기 위해서이다.
- 부하 시험: 6장의 Dummy 클라이언트처럼 가짜 접속자를 만들어 한계를 측정한다. 접속자 수를 단계적으로 늘리며 틱 시간과 지연이 어디서 무너지는지 확인한다.
- 크래시 대응: 서버가 죽으면 원인을 알아야 한다. Windows는 덤프 파일, Linux는 core dump를 남기고, 재시작 시 상태를 복구하는 방법을 정한다.
- 배포: 서버를 새 버전으로 바꿀 때 진행 중인 게임을 어떻게 처리할지(종료 공지, 방 단위 순차 교체)를 미리 정한다.

이 교재는 Linux 서버 운영 도구까지 다루지 않지만, 6장의 Asio 서버 코드는 Linux에서도 그대로 빌드되며 내부적으로 epoll을 사용한다.

[NCS 검토에서 추가한 점] Linux의 서비스 관리자(systemd)로 서버를 서비스로 등록하는 예는 6.14.5절에서 한 번 다룬다. 그 밖의 Linux 운영 도구는 다루지 않는다.

## 1.10 개발 환경, 형상 관리, 진단 도구

서버 프로그래머의 시간은 코드를 쓰는 데만 쓰이지 않는다. 환경을 맞추고, 변경 이력을 관리하고, 문제를 찾는 시간이 그만큼 든다. 같은 코드가 내 컴퓨터에서만 빌드되고 팀원의 컴퓨터에서는 빌드되지 않는다면 그것은 코드의 문제가 아니라 환경 관리의 문제이다. 이 절은 코드 밖의 기본기를 정리한다.

### 1.10.1 개발 환경의 고정

- 언어와 컴파일러: 이 교재의 C++ 코드는 C++20을 기준으로 한다. 팀이 쓰는 컴파일러와 버전(Visual Studio의 도구 집합 버전, g++ 버전)을 문서에 적고 모두 같게 맞춘다.
- 빌드 도구: 프로젝트 파일(.sln)만 공유하면 다른 운영체제에서는 빌드할 수 없다. CMake로 빌드 설정을 파일 하나(CMakeLists.txt)에 적으면 Windows(Visual Studio)와 Linux(g++, clang)에서 같은 소스를 빌드할 수 있다.
- 의존 라이브러리: Asio, MySQL 클라이언트 라이브러리, hiredis 같은 외부 라이브러리의 버전을 기록한다. 소스를 저장소에 포함하거나 패키지 관리자(vcpkg, Conan 등)로 버전을 고정한다. "최신 버전을 받으세요"라는 안내는 몇 달 뒤 빌드가 깨지는 원인이 된다.
- 설정 분리: 개발, 시험, 운영에서 다른 값(포트, DB 주소, 정원)은 코드가 아니라 설정 파일에 둔다(6.14.3절).

6장 실습 1의 서버를 CMake로 빌드하는 CMakeLists.txt는 다음과 같다. Linux에서 g++로 빌드되는 것을 확인했으며, Windows 쪽 설정(ws2_32, mswsock 라이브러리와 _WIN32_WINNT 정의)은 Asio 문서의 안내를 따른 것이다.

```cmake
cmake_minimum_required(VERSION 3.20)
project(ChatServer CXX)

set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

add_compile_definitions(ASIO_STANDALONE)
include_directories(${ASIO_DIR}/include)            # cmake -DASIO_DIR=<Asio 폴더>
find_package(Threads REQUIRED)

add_executable(ChatServer ChatServer.cpp)
target_link_libraries(ChatServer Threads::Threads)

if(WIN32)
  add_compile_definitions(_WIN32_WINNT=0x0A00)      # Windows 10 이상
  target_link_libraries(ChatServer ws2_32 mswsock)
endif()
```

빌드는 `cmake -S . -B build -DASIO_DIR=<Asio 폴더>`로 설정하고 `cmake --build build`로 실행한다.

### 1.10.2 형상 관리(Git)의 기본

- 저장소에 넣는 것: 소스, CMakeLists.txt, 문서, 설정 파일의 견본(config.example.ini). 넣지 않는 것: 빌드 산출물(.exe, .obj, build 폴더), IDE 임시 파일, 비밀번호와 키가 든 실제 설정 파일. 넣지 않을 것은 .gitignore에 적는다.
- 커밋: 하나의 목적을 가진 변경을 하나의 커밋으로 하고, 메시지에 무엇을 왜 바꿨는지 적는다. 빌드가 깨진 상태로 커밋하지 않는다.
- 브랜치: main은 항상 빌드되고 시험을 통과하는 상태로 유지한다. 기능은 별도 브랜치에서 작업하고, 합치기 전에 다른 사람이 변경 내용을 읽는다(코드 리뷰).
- 버전 표시: 배포한 서버에 버전 태그를 붙이고, 같은 버전 번호를 서버 로그와 접속 응답(1.6.3절의 프로토콜 버전)에 남긴다. 문제가 생겼을 때 "이 서버는 어느 소스로 만들었는가"에 답할 수 있어야 한다.
- 비밀 정보의 유출: 키나 비밀번호를 한 번 커밋하면 파일에서 지워도 이력에 남는다. 지우는 것으로 끝내지 말고 해당 비밀을 폐기하고 새로 발급한다.

### 1.10.3 디버깅 방법

- 재현이 먼저이다: 로그에서 시각, 연결 번호, 패킷 종류를 찾아 재현 절차를 만든다. 재현되지 않는 오류는 고쳤는지 확인할 수도 없다.
- 디버거 사용: 서버를 중단점에서 멈추면 클라이언트의 연결이 시간 초과로 끊어질 수 있다. 특정 연결에서만 멈추는 조건부 중단점이나, 멈추지 않고 값을 출력하는 추적 지점(tracepoint)을 쓴다. 멀티스레드 서버는 스레드 창에서 어느 스레드가 멈췄는지 확인한다.
- 크래시 분석: 덤프 파일(Windows)이나 core 파일(Linux)을 심볼 파일과 함께 열어 호출 스택을 본다. 이를 위해 배포 빌드에서도 심볼 파일을 보관한다(6.14.2절).
- 메모리 오류와 정의되지 않은 동작은 눈으로 찾기 어렵다. 샌니타이저로 빌드해서 시험한다(6.13.4절).

### 1.10.4 네트워크 진단 도구

네트워크 프로그램은 코드가 맞아도 환경 때문에 실패한다. 아래 도구로 "어디까지 도달했는가"를 먼저 확인한다.

- 서버가 포트를 열었는가, 그 포트를 누가 쓰고 있는가: Windows는 `netstat -ano`의 결과에서 포트를 찾고, Linux는 `ss -ltnp`를 쓴다. 서버가 시작하자마자 종료한다면 같은 포트를 다른 프로세스가 쓰고 있는지 먼저 확인한다.
- 접속이 되는가: Windows PowerShell의 `Test-NetConnection 127.0.0.1 -Port 9000`, Linux의 `nc -vz 127.0.0.1 9000`. 같은 PC에서는 되는데 다른 PC에서 안 되면 방화벽 허용 규칙을 의심한다.
- 연결 상태: `netstat -an`이나 `ss -tan`에서 ESTABLISHED(연결됨), TIME_WAIT(닫은 뒤 대기), CLOSE_WAIT(상대가 닫았는데 내 쪽이 닫지 않음)를 본다. CLOSE_WAIT가 쌓이면 서버가 연결 종료를 처리하지 않는 오류를 의심한다.
- 패킷 내용: Wireshark로 실제 오가는 바이트를 본다. 표시 필터에 `tcp.port == 9000`을 입력하면 이 서버의 통신만 보인다. 같은 PC 안의 통신(루프백)은 Windows에서 Npcap의 루프백 어댑터를 선택해야 캡처된다. Linux 서버에서는 `tcpdump -i any port 9000`으로 캡처해서 파일로 저장한 뒤 Wireshark로 열 수도 있다.

Wireshark에서 6장의 패킷을 읽는 연습을 한다. 이름이 kim이고 인증 코드가 1234인 HELLO 패킷은 본문이 8바이트("kim|1234")이고 종류가 1이므로, 헤더 4바이트가 `08 00 01 00`(길이 8, 종류 1, 리틀 엔디언)이고 그 뒤에 본문이 이어진다. 연결을 맺을 때의 SYN, SYN-ACK, ACK 세 패킷, 정상 종료의 FIN, 비정상 종료의 RST, 같은 데이터를 다시 보내는 재전송(retransmission)도 구분해서 읽을 수 있어야 한다.

## 1.11 라이선스, 개인정보, 서비스 관련 법규

코드가 동작하는 것과 그 코드로 서비스를 해도 되는 것은 다른 문제이다. 서버 프로그래머도 라이선스와 법규의 영향을 받는다. 이 절은 점검할 항목을 정리한다. 법령과 약관은 바뀌므로 서비스 전에 원문을 확인하고, 해석이 필요한 부분은 법무 담당자와 상의한다. 이 절은 법률 자문이 아니다.

### 1.11.1 라이선스 확인

외부 라이브러리, 엔진, SDK, 에셋을 쓸 때마다 다음 네 가지를 확인한다.

- 상업적 이용이 가능한가.
- 소스 코드를 공개할 의무가 있는가.
- 수익 분배나 사용료 조건이 있는가.
- 다른 사람에게 배포(재배포)할 수 있는가.

오픈소스 라이선스는 크게 둘로 나뉜다. 허용형(MIT, BSD, Boost, Apache 등)은 저작권 고지 같은 조건만 지키면 상업 서비스에 쓸 수 있다. 상호주의형(GPL, LGPL, AGPL 등)은 조건에 따라 소스 공개 의무가 생긴다. 특히 AGPL은 수정한 프로그램을 네트워크 서비스로 제공할 때도 사용자에게 소스를 제공해야 할 수 있어서, 서버 프로그램에서는 사용 전에 반드시 확인한다.

이 교재에서 쓰는 것을 예로 들면, Asio는 Boost Software License로 배포된다(소스 파일 머리말에 적혀 있다). MySQL Community Edition은 GPL 계열 라이선스이고 상용 라이선스가 따로 있다. Redis는 버전에 따라 라이선스가 바뀐 적이 있으므로 설치한 버전의 라이선스를 확인한다. Unity, Unreal, Steamworks는 각자의 약관과 수익 분배 조건이 있다. 어느 것이든 사용하는 버전의 라이선스 원문을 직접 확인하는 것이 원칙이고, 이 교재의 설명을 근거로 삼지 않는다.

저작권은 코드에만 해당하지 않는다. 프로젝트에 넣는 폰트, 이미지, 사운드, 에셋 스토어에서 받은 에셋도 사용 범위가 정해져 있다. 인터넷에서 복사한 코드는 출처와 라이선스를 확인하고, 학교 과제와 포트폴리오에서도 출처를 밝힌다.

### 1.11.2 개인정보와 로그

- 수집 최소화: 서비스에 필요한 항목만 받는다. 2~4장의 채팅은 이름과 인증 코드만 쓴다.
- 보관과 파기: 보관 기간을 정하고 기간이 지나면 삭제한다. 탈퇴하면 삭제하는 절차가 있어야 한다.
- 접근 통제와 기록: 운영자가 개인정보를 조회할 수 있다면 누가 언제 무엇을 봤는지 기록한다.
- 로그: 비밀번호와 인증 토큰은 로그에 남기지 않는다. 접속한 IP 주소는 공격에 대응하는 데 필요하므로 남기되 개인정보처럼 다룬다. 로그를 볼 수 있는 사람을 제한하고, 보관 기간을 정하고, 필요 이상으로 자세하면 일부를 가린다.
- 아동: 만 14세 미만 아동의 개인정보를 처리하려면 법정대리인의 동의를 받아야 한다(개인정보 보호법 제22조의2). 가입 절차에 연령 확인과 법정대리인 동의가 필요한지 점검한다.
- 서비스 지역: 해외에 서비스하면 그 지역의 법(예: 유럽의 GDPR)이 적용될 수 있다.
- 인증 제도: 서비스 규모에 따라 정보보호 및 개인정보보호 관리체계 인증(ISMS-P) 같은 제도의 적용 대상이 될 수 있다. 서비스를 기획할 때 대상 여부를 확인한다.

### 1.11.3 게임 서비스의 규제와 서버 설계

게임은 일반 앱과 달리 게임 관련 법령의 적용을 받는다. 서버 설계에 직접 영향을 주는 예로 확률형 아이템이 있다. 게임산업진흥에 관한 법률의 개정으로 2024년 3월 22일부터 온라인 게임에서 유상 구매가 직접 또는 간접적으로 가능한 확률형 아이템은 확률 정보를 공개해야 한다. 공개 대상의 범위와 표시 방법, 위반했을 때의 조치는 문화체육관광부의 해설서와 법령으로 확인해야 한다. 이 밖에 게임물 등급분류 같은 제도도 서비스 전에 확인한다.

법을 해석하는 일은 법무 담당자의 몫이고, 서버 프로그래머의 일은 이런 요구에 대응할 수 있는 구조를 만드는 것이다. 확률형 아이템을 예로 들면 다음과 같이 설계한다. 이것은 법 해석이 아니라 설계 권장 사항이다.

- 추첨은 서버가 한다. 클라이언트가 결과를 정하면 안 된다는 1.8절의 원칙과 같다.
- 확률을 코드에 고정하지 않고 데이터 테이블로 관리한다. 확률표에 버전과 적용 시각을 기록해서 "그 시점에 어떤 확률이 적용되었는가"에 답할 수 있게 한다.
- 추첨 결과를 로그로 남긴다. 누가, 언제, 어느 버전의 확률표로, 무엇을 얻었는지를 기록한다.
- 유상 재화와 무상 재화의 지급 경로를 구분해서 기록한다. 무상 재화가 유상 재화로 교환되는 경로가 있는지도 점검 대상이다.

## 1.12 1장 연습 문제

1. 클라이언트-서버, P2P, 릴레이의 연결 수를 접속자 8명일 때 각각 계산하고, 상태의 기준이 어디에 있는지 비교하라.
2. 틱이 30Hz인 서버가 클라이언트 500명에게 한 번에 150바이트의 상태를 보낼 때 필요한 대역폭(Mbps)을 계산하라.
3. 위치 동기화는 상태 동기화로, 발사는 이벤트로 보내야 하는 이유를 패킷 손실 상황을 들어 설명하라.
4. TCP로 메시지를 보낼 때 한 번의 send가 두 번의 recv로 나뉘어 도착하는 상황과, 두 번의 send가 한 번의 recv로 합쳐 도착하는 상황을 그림으로 그리고 수신 코드가 어떻게 처리해야 하는지 설명하라.
5. 데이터베이스 질의를 게임 루프에서 직접 호출했을 때 생기는 문제를 설명하고, 해결 구조를 그려라.
6. 클라이언트가 보낸 "이동 요청"을 서버가 검증하려면 어떤 값을 확인해야 하는지 세 가지 이상 적어라.
7. 서버를 실행한 상태에서 Windows는 `netstat -ano`, Linux는 `ss -ltnp`로 서버가 연 포트와 그 포트를 쓰는 프로세스를 찾아라. 같은 포트로 서버를 한 번 더 실행하면 어떤 오류가 나는지 확인하고, `Test-NetConnection`(Windows) 또는 `nc -vz`(Linux)로 접속이 되는지 본 다음, 서버를 종료한 뒤 같은 명령의 결과가 어떻게 달라지는지 적어라.
8. Wireshark나 tcpdump로 6장 실습 1의 서버에 클라이언트를 접속시켜 HELLO 패킷을 캡처하라. 헤더 4바이트가 어느 바이트인지 표시하고, 연결을 맺는 세 패킷(SYN, SYN-ACK, ACK)과 연결을 끊는 패킷(FIN 또는 RST)을 찾아라.
9. 6장 실습 1의 서버를 빌드하는 CMakeLists.txt를 직접 작성하고, 저장소를 새 폴더에 복제해서 처음부터 빌드하라. 빌드되지 않는다면 저장소에 빠져 있던 파일이나 설정이 무엇이었는지 적어라.
10. 팀 프로젝트의 `.gitignore`에 넣을 항목을 정하고 각각 저장소에 넣으면 안 되는 이유를 한 줄씩 적어라. 비밀번호가 든 파일을 실수로 커밋했을 때 해야 할 일을 순서대로 적어라.
11. 이 교재의 실습에서 쓰는 라이브러리나 엔진 세 가지를 골라 라이선스 원문을 찾아 읽고, 1.11.1절의 네 가지 질문에 답하라. 근거로 삼은 원문의 위치(주소와 버전)를 함께 적어라.
12. 2~4장 또는 6장의 채팅 서버가 남기는 로그를 보고 개인정보에 해당할 수 있는 항목을 찾아라. 남길 항목, 남기지 않을 항목, 보관 기간을 정하고 이유를 적어라.
